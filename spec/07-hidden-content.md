# 07. Скрытый контент

Наследник «[ссылка зашифрована 🔐]» из прототипа. Два режима: **для всех** и **для конкретного ника**.

## Что можно скрыть
В черновике клиента:
- «Скрыть ссылки»: все `url` и `text_link` в тексте заменяются плашкой `[ссылка скрыта 🔐]`;
- «Скрыть сообщение»: весь текст заменяется плашкой `[сообщение скрыто 🔐]`. Медиа остаётся видимым,
  скрыть можно только текст или подпись.

Скрытая часть (`hidden_payload`) — это JSON `{text, entities}` в канонической форме (JCS), текст 1…4096 UTF-16
единиц (как сообщение Telegram), JSON не больше **24 576 байт** (`hidden_payload_max`). Других полей нет, кроме
`pad` и `post_pk` у «лично для» (ниже). Конверт с таким blob больше 3000 байт и уходит документом (04, «Большой конверт»);
прежний предел ≈ 700 символов снят 2026-10-17. Предел 24 КБ выбран так, чтобы запись ленты
с blob «лично для» поместилась в ответ `feed.get` (16 частей по 4000 символов): худшая допустимая запись
(blob на пределе, ник из 128 четырёхбайтовых кодовых точек, `excerpt` из управляющих символов) вместе с обёрткой
ответа занимает около 34,7 КБ при пределе ответа 47 951 байт.

## Выравнивание длины (2026-10-17)
Blob «лично для» лежит в публичной ленте, поэтому его длина не должна выдавать длину текста:
- payload дополняется полем `"pad"` из пробелов так, чтобы JCS-длина была кратна **256 байтам**
  (`hidden.padded` в эталонном клиенте). Получатель поле игнорирует; `pad`, содержащий не только пробелы, — ошибка;
- контейнер файлов (ниже) дополняется нулями по схеме **Padmé** (Nikitin et al., PETS 2019: раскрывается
  O(log log n) бит, запас не больше 12 %), но не больше предела 20 МБ. Размеры файлов — в payload, хвост из нулей
  отбрасывается; ненулевой хвост — подмена (ошибка).

Векторы: `padding` в `test-vectors/veil-v1.json` (размер блока, длины Padmé). Режим «для всех» не выравнивается:
сервер и так расшифровывает его ключом из кнопки.

## Режим «для всех»
1. Клиент генерирует `K` (32 байта) и шифрует: `blob = nonce[24] || XChaCha20-Poly1305(K, nonce, hidden_payload,
   aad = "veil/v1/hidden")`. Сервер проверяет, что blob открывается ключом `K` и payload корректен
   (иначе `E_MALFORMED`): кнопка не должна оказаться сломанной.
2. В `post.create` передаёт `body.hidden = {"mode":"all","blob":"<b64url>","key":"<b64url K>"}`.
3. Сервер публикует пост с кнопкой «👁 Показать» и **сам** добавляет после текста строку
   «🙈 есть скрытое — нажмите «Показать»» (локаль `render.hidden_all`; до 2026-10-17 — «Расшифровать»: ключ лежит в
   кнопке, и любой участник может его достать через MTProto, поэтому режим честнее называть «спрятать», а не
   «зашифровать»; решено 2026-10-15: вид поста решает сервер, пометка есть при любом клиенте). Плашки внутри текста («[ссылка скрыта 🔐]»,
   «[сообщение скрыто 🔐]») ставит клиент по своему усмотрению; эталонный клиент их ставит.
   Кнопка — одна на пост, других кнопок под постами нет (минимум кнопок под постами). `callback_data = "h:<n в base36>:<K в base64url>"`
   (≤ 64 байт).
   **Хранение K (пересмотрено 2026-10-15).** Telegram снимает кнопки при любой правке сообщения, если не
   передать их заново, а пост правится при каждом новом ответе (строка ответов). Поэтому сервер хранит `K`,
   но только **зашифрованным** ключом из каталога секретов (`hidden_key_enc`, HKDF от `pepper`). Утечка одной
   базы (или её бэкапа) скрытый текст по-прежнему не раскрывает. Взлом работающего сервера раскрывает — но
   текст «для всех» и так доступен любому участнику группы нажатием кнопки; режим защищает от случайного
   взгляда и поиска, а не от участников.
4. Нажатие: сервер берёт `K` из `callback_data`, расшифровывает `blob` и показывает содержимое
   **эфемерным сообщением** (Bot API 10.2+, `ephemeral_message_parameters`), которое видит только
   нажавший. Запасной вариант: `answerCallbackQuery` с `show_alert` (≤ 200 символов) и обрезкой.
5. ID нажавшего сервер не записывает: он нужен только как `receiver_user_id` эфемерного сообщения.
   Показать скрытое может **любой** участник группы, каждый своим нажатием; показанное видит только нажавший.
   Поведение Telegram (проверено 2026-10-15, два аккаунта): эфемерное сообщение остаётся на устройстве,
   где его получили (переживает перезапуск приложения), на другие устройства того же аккаунта не приходит.
   Чтобы увидеть на другом устройстве — нажать кнопку там.
6. Альбом: кнопку к альбому прикрепить нельзя, поэтому пост публикуется шапкой с текстом и кнопкой,
   а альбом — ответом на неё без подписей.

Утечка базы без доступа к сообщениям Telegram не раскрывает скрытый текст.

**Требует проверки вживую** (OPEN_QUESTIONS, п. 1): видит ли эфемерное сообщение участник, которому
запрещено писать в группе.

## Единая таблица (2026-10-16)
Какой контент как скрывается — одна таблица на сервере и её зеркало в клиенте
(`veil/core/privacy.py`); кнопки клиента и проверка `post.check` берутся из неё, а не из частных проверок:

| контент \ режим | нет | ссылки | всё (для всех) | лично для |
|---|---|---|---|---|
| текст | да | если есть ссылки | да | да (текст) |
| медиа с подписью | да | если есть ссылки | да (медиа + подпись по кнопке) | да (файл-контейнер) |
| кружок, стикер | да | — | да | да (файл-контейнер) |
| альбом | да | если есть ссылки | да | да (файл-контейнер) |
| опрос | да | — | — | — |

## «Лично для» с медиа (файл-контейнер, 2026-10-16)
Медиа нельзя зашифровать на ключ получателя средствами Telegram, поэтому шифрует клиент:
1. Скачивает файлы своего владельца (Bot API отдаёт ботам до **20 МБ** — общий предел).
2. `container = nonce[24] ‖ XChaCha20-Poly1305(file_key, nonce, файл1‖файл2‖…, aad="veil/v1/file")`.
3. В `hidden_payload` добавляются `files` (вид, имя, mime, размер — по порядку) и `file_key`; payload
   запечатывается на `enc_pk` получателя как обычно.
4. Контейнер уходит серверу документом с подписью-плашкой, конверт — `hidden = {"mode":"to", …, "file": true}`.
   Сервер контейнер **не публикует** (в группе — плашка и «лично для …»), хранит его `file_id`.
5. Получатель видит в ленте `hidden_file: true`; бот предлагает владельцу кнопку и только по ней забирает контейнер
   `hidden.file` (у бота из поля `bot`), расшифровывает и присылает файлы тем же видом (фото, видео, кружок, альбом…)
   с безопасными именем и MIME: файлы прислал другой человек. Проверено вживую 2026-10-16.
Сервер узнаёт, какой бот забрал файл, — но связь «личность → бот» он и так знает по привязке (`bind_hash`).

## Скрытый альбом показывается одним сообщением (2026-10-16)
`sendMediaGroup` не бывает эфемерным, поэтому альбом «для всех» по кнопке показывается одним эфемерным
`sendRichMessage` (Bot API 10.x): коллаж фото/видео (или список документов/аудио) и подпись абзацем
(entities переводятся в дерево `RichText`, `render.RichText`). Если Telegram rich-сообщение не принял —
запасной путь: элементы по одному.

## «Скрыть всё» у медиа (добавлено 2026-10-15)
`body.hidden = {"mode":"all","blob":..,"key":..,"media":true}` у поста с медиа (фото, видео, GIF, документ, аудио,
голосовое, кружок, стикер, альбом; опрос — нет, `E_UNSUPPORTED`). Сервер **не публикует медиа в группу**: только
шапку с видимым текстом (подпись-плашка «[сообщение скрыто 🔐]»), пометкой и кнопкой. Нажатие показывает
нажавшему медиа эфемерными сообщениями (`sendPhoto`… с `ephemeral_message_parameters`, по `file_id`
бота-публикатора) и подпись из `hidden_payload` (может быть пустой). `file_id` хранится в `hidden_media`.
Медиа при этом не шифруется: его видят сервер и Telegram, как и любое медиа. Режим скрывает от участников,
которые не нажали кнопку. Правка `media` у таких постов — `E_UNSUPPORTED`; `replace`/`append` правят видимый текст.
Клиент: одиночное медиа копируется с подписью-плашкой, альбом — `copyMessages` с `remove_caption`.

## Режим «для конкретного ника»
1. Клиент находит получателя: `nick.lookup {"nick":"Петя","tag":"k2m9xq"}` → цепочка «корень → устройство →
   ключ шифрования» и ОБЯЗАН проверить её, метку и закрепление (02, «Проверка получателя»): иначе сервер мог бы
   подставить свой ключ. Ключ шифрования получателя меняется раз в 7 дней, поэтому его не запоминают надолго,
   а берут свежим перед каждой отправкой; закрепляется `id_pk`.
2. Шифрует: `blob = crypto_box_seal(hidden_payload, enc_pk)`. В payload — `"post_pk"` этого поста (тот же, что
   `body.post_pk`): sealed box не говорит, кто запечатал, и без привязки blob из публичной ленты можно было бы
   приложить к своему посту тому же адресату — получатель увидел бы чужое сообщение под чужой подписью (2026-10-19).
3. `body.hidden = {"mode":"to","to_pk":"<b64url enc_pk>","blob":"<b64url>"}`.
4. В группе сервер добавляет после текста строку «🔐 лично для Петя·k2m9xq — прочитать может только он»
   (локаль `render.hidden_to`; прежнее «скрыто для Петя» читалось как «от Пети скрыто» — изменено 2026-10-15)
   без кнопки: сервер расшифровать не может, посторонним прочитать нечем, получатель увидит текст в своём
   боте. Кнопок-пояснений не делаем (минимум кнопок). Ник·метка фиксируются на момент публикации, как `nick_at_post`.
   Получатель должен иметь ник и зарегистрированное устройство с действующим ключом шифрования (`device.set`,
   `nick.set`), иначе `E_NOT_FOUND`.
5. Получатель узнаёт о скрытом для себя так: клиент скачивает ленту (`feed.get`), где для таких постов
   есть `hidden_for` и `hidden_blob`, ищет `hidden_for` среди своих хранимых ключей шифрования (текущего и прежних,
   до `exp` + 30 дней) и расшифровывает подходящим `enc_sk`. Получилось и `post_pk` внутри совпал с `post_pk` записи
   ленты — показывает владельцу «Вам лично от <подпись поста>, пост №N: …»; не совпал или его нет — отбрасывает.
   Так сервер не узнаёт, кто получатель забрал сообщение.

## Кнопки
Это **единственная** кнопка под постами в группе. Остальные действия выполняются пересылкой поста
своему боту. Кнопки нельзя прикрепить к альбомам: для альбома с режимом «для всех» кнопка
ставится на сообщение-шапку, которое сервер отправляет перед альбомом.
