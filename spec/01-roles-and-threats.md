# 01. Роли и модель угроз

## Участники
| Роль | Кто управляет | Что видит |
|---|---|---|
| Человек | пользователь | всё своё; 12 слов записаны у него и больше нигде |
| Клиент (свой бот) | сам человек | ключ устройства, ключи шифрования, токены, черновики, связь «мой пост ↔ секрет» (не 12 слов, 02) |
| Общий бот | админ проекта | **всё о своих пользователях**, включая Telegram ID. Это доверенный режим |
| Эмитент | админ проекта | Telegram ID человека и сколько токенов он взял. **Не видит**, какие токены выдал |
| Приёмный бот | админ проекта | ID бота-отправителя (в момент запроса), содержимое конверта |
| Публикующие боты | админ проекта | только то, что публикуют |
| Владелец @username приёмного бота (в том числе перехватившего имя) | тот, кто сейчас владеет именем | при первом обращении клиента (04, «Первое касание») — факт, что бот X (его ID и имя) обратился к нему, и время; без контента, ключей, токенов и ID человека |
| Telegram | Telegram | переписку человека с его ботом **открытым текстом**, bot-to-bot трафик (контент открыт, конверт зашифрован) |
| Читатели группы | все | опубликованные посты, ники с меткой |

## Что разделено архитектурно
- **Эмитент ↔ сервер.** Эмитент знает человека, но токены выдаются вслепую (POPRF, 03). Сервер
  при предъявлении токена не может узнать, кому он был выдан. Ключ эмитента один на всех и закреплён
  у клиента, поэтому «пометить» человека отдельным ключом нельзя (03, 2026-10-16).
- **Человек ↔ бот.** Человек никогда не сообщает серверу и эмитенту, какой у него бот. Запрос токенов
  человек переносит от своего бота эмитенту **без указания автора** (03, «перенос запроса»).
- **Пост ↔ бот.** Сервер не сохраняет, с какого бота пришёл пост. Право управлять постом доказывается
  секретом поста (`post_secret`), сервер хранит только его открытый ключ.
- **Личность ↔ устройство.** Корень личности (12 слов) не живёт на машине бота; бот действует ключом
  устройства, который можно отозвать (02).
- **Лента ответов публичная и одинаковая для всех.** Клиент узнаёт об ответах на свои посты, скачивая
  общую ленту и фильтруя её у себя. Из запроса ленты сервер не узнаёт, какие посты интересуют клиента.

## Анонимность: от кого что скрыто (формализовано 2026-10-16)
«Анонимно» — это три разные защиты от трёх разных наблюдателей.

| Наблюдатель | Что знает об анонимном посте | Почему |
|---|---|---|
| Читатели группы и другие пользователи | ничего, кроме текста и номера | подписи нет; одноразовый ключ; ник не показывается |
| Утечка базы сервера или её бэкапа | ничего (кроме опроса, который ещё ждёт публикации: у него виден бот-отправитель, 08) | у постов нет ID ботов и личностей; привязка бота — HMAC с перцем вне базы; потраченный токен не связан с выдачей |
| Честный сервер (не пишет лишнего) | ничего | в журналах нет ID ботов, личностей и содержимого (08) |
| **Взломанный работающий сервер** или администратор, который начал записывать | **с какого бота пришёл пост**, в момент приёма | bot-to-bot: Telegram сообщает ID отправителя. Если этот же бот зарегистрирован как устройство личности (`device.set`), пост связывается с личностью. По времени тоже: личный запрос и анонимный пост от одного бота рядом по времени |
| Эмитент (тот же администратор) | кто и сколько токенов брал, но не какие | слепая подпись; ключ эмитента закреплён у клиентов |
| Telegram | **всё**: кто человек, его бот, текст | человек пишет своему боту обычным сообщением; Veil не защищает от Telegram |
| Сетевой наблюдатель | ничего содержательного | весь трафик — HTTPS к Telegram |

Следствия:
1. Анонимность от **других людей** — полная и держится на криптографии.
2. Анонимность от **сервера** держится на том, что он не записывает ID ботов. При взломе работающего сервера
   анонимные посты связываются с ботом-отправителем. **Для максимальной анонимности анонимные посты нужно слать
   с отдельного бота, который не зарегистрирован как устройство личности** и не используется для постов с ником.
   Эталонный клиент шлёт посты без ника одноразовым ключом и поддерживает случайную задержку публикации.
3. От **Telegram** анонимности нет и не может быть в этой архитектуре.

## Угрозы и что от них защищает
| Угроза | Защита | Остаточный риск |
|---|---|---|
| Утечка базы сервера | Нет Telegram ID, нет ID ботов у постов, хешированные токены, шифрованный скрытый контент, «перец» для HMAC вне базы | Видны публичные данные: посты, ники, публичные ключи; у опроса, который ещё не опубликован, — ID бота-отправителя (08) |
| Взлом работающего сервера | Криптографической защиты от наблюдения в реальном времени нет | Связь «бот → анонимный пост» (см. «Анонимность»); K скрытых «для всех» |
| **Сервер подставляет ключ получателя «лично для»** | Цепочка подписей «корень → устройство → ключ шифрования», проверка метки, закрепление `id_pk` и `seq` у отправителя (02) | Первый контакт с подделанной личностью-двойником: от него защищают уникальность ник·метки и медленная метка |
| **Сервер помечает человека своим ключом эмитента** | Ключ эмитента закреплён у клиента из публичного репозитория (03) | Владелец должен взять `keys.json` из репозитория, а не у сервера |
| Сервер откатывает базу из бэкапа | Бот владельца перерегистрирует устройство своим сертификатом, отправители замечают откат по `seq` (08) | Токены за этот день можно потратить второй раз |
| **Кража файлов бота** (`data/`: взлом машины, бэкап, хостинг) | В файлах нет 12 слов; ключ устройства отзывается восстановлением по словам; привязка к боту — без его токена ключ бесполезен | До отзыва вор действует от имени личности; читает «лично для» на хранимые ключи (до ~6 недель); видит номера своих (то есть ваших) постов за срок хранения (по умолчанию 30 дней) |
| **Кража 12 слов** | Слова не хранятся на машине и не проходят через Telegram (02; исключение — режим пула `words_once`, который оператор включает явно) | Личность потеряна: у вора те же права. Прошлая личная переписка не раскрывается (ключи шифрования не из слов) |
| Утечка токена бота пользователя | Конверты подписаны ключом устройства, а его у вора нет | Вор читает, что приходит боту; отзывайте токен в @BotFather |
| Злоумышленник подделывает конверт | Подпись Ed25519, привязка контента по `file_unique_id` и хешу текста | — |
| Чужое «лично для» под своим постом (blob из публичной ленты приложен к посту тому же адресату) | В зашифрованном лежит `post_pk` поста, получатель сверяет его с лентой (07) | — |
| Подмена номера поста ником или текстом («№1» в нике) | Номер берётся только из строки шапки целиком; «№» в нике запрещён (02, 06) | — |
| Отпечаток часов клиента (`id` и `ts` конверта) | `id` — случайные 128 бит, `ts` округлён вниз до 10 с (04) | Сдвиг часов по многим конвертам статистически оценить можно |
| Спам с множества ботов | Каждое действие стоит токен; токены выдаются на человека (Telegram ID у эмитента) | Мультиаккаунты Telegram дают каждому аккаунту свой лимит |
| Повтор конверта (replay), параллельные копии | `id` и окно `ts` ±300 с; резерв токена за `id` конверта; действие и трата токена в одной транзакции; повтор после сбоя получает первый результат (03, 05) | — |
| Сопоставление по времени (эмитент ↔ публикация) | Токены берутся пачкой заранее на 7 дней; опциональная случайная задержка публикации | При малом числе пользователей сопоставление возможно статистически |
| Блокировка серверного бота | Роли разнесены по ботам, пул публикующих ботов, конфиг без перекомпиляции | Блокировка группы целиком |

## Граница доверия: сервер не верит клиенту (сверено 2026-10-20)

Клиент может быть написан заново на любом языке и прислать что угодно. Поэтому всё, что видят другие (вид поста,
подпись, номер, лимиты, получатель), сервер выводит сам — из того, что получил от Telegram, из своей базы и своими
ключами. Что сообщает клиент, сервер только проверяет.

| Операция | Что присылает клиент | Что сервер берёт или проверяет сам |
|---|---|---|
| любой конверт | подпись, `ts`, `id`, `auth` | подпись ключом из `auth`, время ±300 с, повтор `id`, допустимый `auth.mode` для операции, строгий JSON |
| платная операция | токен | выход PRF ключом эмитента, день (UTC сервера), однократность; трата — в транзакции действия |
| `post.create`, `post.edit` | `content` (вид, хеши текста и форматирования, файлы) | сами сообщения — из апдейтов Telegram, **только от бота, приславшего конверт**; вид, хеши и `file_unique_id` пересчитываются и сверяются; публикуются по `file_id` из этого снимка |
| `post.create` | `post_pk`, `reply_to`, `hidden` | номер `№N`, ник и метка — из базы по ключу устройства; `reply_to` — существующий опубликованный пост; длина — по своему рендеру; таблица скрытия — своя (07); «для всех» — сервер расшифровывает и проверяет содержимое; «лично для» — подпись «Петя·k2m9xq» из своей базы по ключу получателя |
| `post.edit`, `post.delete` | подпись ключом поста | владение — `post_pk` из базы; окно 24 ч и 5 правок — по базе; правка медиа — только бот-публикатор |
| `device.set`, `enc.set` | сертификаты | цепочка подписей «корень → устройство → ключ шифрования», `seq` и срок не из будущего, привязка к боту — HMAC от ID бота из Telegram; метку считает сервер |
| `nick.set`, `nick.lookup` | ник | нормализация, проверка и ключи похожести — на сервере; уникальность — индекс базы |
| `hidden.file`, `feed.get`, `post.check` | номер поста, курсор, черновик | только чтение; лимиты частоты; `post.check` — подсказка, на неё ничто не опирается |
| `market.redeem`, `market.key` | лицензия, ключ установки, сертификат | плагин платный — по своему подписанному индексу; лицензия — секретным ключом магазина; однократность — по базе; сертификат — своим `server_sig` |
| эмитент | запрос `VEILREQ` | лимит по Telegram ID отправителя (HMAC), только люди, пересылка без видимого бота, валидность точек |
| магазин | запрос `VEILLIC` | цена и плагин — по своему индексу; сумма и валюта — в `pre_checkout_query` и `successful_payment`; выдача — только после оплаты |

### Правила, которые есть у обеих сторон

Клиент повторяет часть правил, чтобы не предлагать владельцу то, что сервер отклонит. Решает всегда сервер; копии
сверяются общими векторами (`test-vectors/veil-v1.json`), и тесты обеих реализаций падают при расхождении:

| Правило | Вектор |
|---|---|
| строгий JSON, JCS, base64url | `jcs`, `json_reject`, `base64url` |
| конверт, ответ, многочастный ответ | `envelope`, `envelope_reject`, `response`, `response_parts` |
| хеши текста и форматирования | `text_sha256`, `entities_sha256` |
| ник, похожие ники, метка | `nick`, `nick_key`, `tag` |
| таблица скрытия и состав альбома | `hide_table`, `album_kinds` |
| скрытое содержимое, выравнивание | `hidden_all`, `hidden_to`, `hidden_reject`, `padding` |
| выдача токенов | `poprf_cross_request`, `issue_cross_request`, `issue_reject` |
| числовые ограничения, коды ошибок, формат `kid` | `limits`, `error_codes`, `formats` |
| маркет: индекс, пакет, лицензия | `market` (в том числе `market.reject`), `license-cross.json` |

Длину поста клиент не считает сам: спрашивает сервер (`post.check`).

## Явно вне защиты
- Telegram как платформа (он видит связку «человек → его бот → текст»).
- Стилометрия: узнавание человека по манере письма.
- Вредоносный код на машине бота **во время работы**: он пользуется ключом устройства через сам бот.
  Ограничение ущерба — отзыв устройства по 12 словам (02).
- Общий бот: его пользователи доверяют админу.
