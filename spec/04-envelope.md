# 04. Конверт

## Транспорт
Клиент и приёмный бот общаются по **bot-to-bot** Telegram (Bot API 10.0+). Режим должен быть включён
у обоих ботов в @BotFather; проверено на тестовых ботах 2026-10-14.

Одна операция состоит из:
1. **Контента** (если есть): клиент копирует сообщение владельца в чат с приёмным ботом через
   `copyMessage` (альбом — `copyMessages`). Копия сохраняет форматирование и медиа и не показывает источник.
2. **Конверта**: текстовое сообщение `VEIL1 <base64url(sealed)>`, отправленное **ответом**
   (`reply_parameters`) на первое сообщение контента. Так сервер получает контент как
   `reply_to_message` в своей нумерации сообщений.

Почему не `file_id` и не номер сообщения: `file_id` у каждого бота свой, а номера сообщений в личной
переписке у каждой стороны свои. Контент сверяется по `file_unique_id` (одинаков для всех ботов)
и по хешу текста (см. «Привязка контента»).

Альбом: конверт отвечает на первый элемент; сервер собирает остальные по `media_group_id`
(ожидание до 3 секунд после последнего элемента).

## Шифрование
`sealed = crypto_box_seal(plaintext, inbox_enc_pk)` (libsodium sealed box: X25519 + XSalsa20-Poly1305).
- Go: `golang.org/x/crypto/nacl/box` `SealAnonymous` / `OpenAnonymous`.
- Python: PyNaCl `SealedBox`.

`plaintext` = байт формата + UTF-8 JSON в канонической форме (JCS, см. ниже).
Байт формата: `0x00` — JSON без сжатия (единственный формат v1); `0x01` зарезервирован под zstd,
в v1 его НЕ ДОЛЖНЫ отправлять, сервер отвечает `E_DECRYPT`.
Размер JSON — не больше **3000 байт**: так `VEIL1 ` + base64url помещается в одно сообщение (4096 символов).

### Большой конверт (2026-10-17)
Конверт больше 3000 байт (длинный скрытый текст, 07) отправляется **документом** с подписью ровно `VEIL1D`
ответом на первое сообщение контента; содержимое файла — тот же текст `VEIL1 <base64url(sealed)>`. JSON такого
конверта — не больше **65 536 байт** (`envelope_doc_json_max` в векторах `limits`). Сервер скачивает документ
(`getFile`, не больше соответствующего размера base64) в слоте пула конвертов и дальше обрабатывает его как обычный
конверт; ответ приходит ответом на документ. Текстовый конверт больше 3000 байт сервер отвергает (`E_DECRYPT`).
Клиент ДОЛЖЕН отправлять текстом всё, что помещается в 3000 байт.

### Адрес приёмного бота (2026-10-17)
Клиент пишет приёмному боту по **числовому ID** из подписанного `keys.json` (`inbox_bots`, 02) и принимает ответы,
подсказки `VEIL1E` и вложения только от ботов с этими ID. @username используется, только пока сервер ID не
публикует: имя бота может сменить владельца, и тогда контент открытым текстом ушёл бы чужому. Отправка bot-to-bot
по ID проверена вживую 2026-10-17.

Приёмных ботов может быть несколько (один сервер, одни ключи). Если бот перестал принимать сообщения (Telegram
отвечает 403 или «chat not found»), запрос без контента клиент отправляет следующему из `inbox_bots` и дальше пишет
ему (2026-10-19). Конверт с контентом и его повтор — только тому боту, которому ушёл контент: у другого бота
сообщения с этим номером нет. Запрос к конкретному боту (`hidden.file` — тому, кто держит файл, поле `bot` ленты)
тоже не переключается. Ответ сопоставляется с конвертом по паре «чат, номер сообщения»: номера у каждого бота свои.

Сервер перебирает все действующие ключи `inbox_enc` (при ротации их два), пока один не расшифрует
конверт; неудачная попытка sealed box дешёвая. Затем проверяет, что поле `kid` совпадает с ключом,
который подошёл (`E_MALFORMED` иначе).

Ответы сервера шифруются на `resp_pk` из конверта (одноразовый X25519 клиента) и отправляются
сообщением `VEIL1R <base64url>` ответом на конверт. Ответ **подписан** ключом `server_sig`
(см. 02): поле `sig` = Ed25519 по `"veil/v1/response\n" || JCS(ответ без sig)`. Клиент ДОЛЖЕН проверить
подпись и что `re` равно `id` его конверта. Формат ответа: 09.

## Структура (plaintext)
```json
{
  "v": 1,
  "op": "post.create",
  "id": "01JA...ULID",
  "ts": 1792000000,
  "kid": "i1",
  "resp_pk": "<b64url X25519>",
  "auth": {"mode": "identity", "pk": "<b64url Ed25519>"},
  "token": {"scheme": "poprf-r255-v1", "kid": "2026-W42", "day": "2026-10-14",
            "input": "<b64url>", "output": "<b64url>"},
  "content": {"kind": "text", "text_sha256": "<hex>", "files": ["<file_unique_id>"]},
  "body": { ... зависит от op ... },
  "sig": "<b64url Ed25519>"
}
```
| Поле | Обязательно | Смысл |
|---|---|---|
| `v` | да | версия протокола, **целое число** (`true` и другие не целые значения — `E_VERSION`); сервер принимает `v` и `v-1` |
| `op` | да | операция (см. 05) |
| `id` | да | id операции в записи ULID (26 символов Crockford Base32); повтор `id` в течение 24 ч отклоняется (`E_REPLAY`) |
| `ts` | да | unix-время клиента, **целое число** (не логическое, не строка — `E_MALFORMED`), допуск ±300 с в обе стороны, границы ±300 допустимы, ±301 — `E_CLOCK` |

Почему допуск симметричный. Повтор отсекается по `id` в течение 24 ч с момента получения, `ts` в этом не участвует,
поэтому конверт «из будущего» окно повтора не расширяет. Запас в будущее нужен клиентам, у которых часы спешат;
асимметричный допуск ударил бы по ним и ничего не дал бы.

Эталонный клиент кладёт в `id` 128 случайных бит без метки времени и округляет `ts` вниз до 10 с (2026-10-19): точное
время клиента позволяло бы серверу различать устройства по сдвигу часов и связывать посты разных ботов одной машины.
Статистически сдвиг часов по многим конвертам оценить всё равно можно; от этого защищает только отдельная машина.
| `kid` | да | каким `inbox_enc` зашифровано (подписанное подтверждение, сервер сверяет с подошедшим ключом) |
| `resp_pk` | да | куда шифровать ответ |
| `auth.mode` | да | `identity` (от имени личности: подписано **ключом устройства**, 02), `ephemeral` (анонимно, одноразовый ключ), `post_secret` (управление постом) |
| `auth.pk` | да | публичный ключ, которым подписан конверт; при `identity` — `dev_pk`, сервер находит по нему личность |
| `token` | для платных `op` | см. 03 |
| `content` | если есть контент | описание приложенного контента для привязки |
| `body` | по `op` | параметры операции |
| `sig` | да | подпись Ed25519 по канонической форме всего объекта без поля `sig` |

## Каноническая форма для подписи
JSON Canonicalization Scheme (RFC 8785). Подписывается строка
`"veil/v1/envelope\n" || JCS(envelope без sig)`.

## Привязка контента
Сервер ДОЛЖЕН проверить, что полученный контент совпадает с описанием в `content`:
- `text_sha256` = hex(SHA-256(`"veil/v1/text\n"` || UTF-8 текста)). Текст: `text` сообщения, `caption`
  медиа (пустая строка, если подписи нет), `question` опроса. Для альбома — первая непустая подпись.
- `entities_sha256` (обязательно с 2026-10-16) = hex(SHA-256(`"veil/v1/entities\n"` || JCS(проекция))): форматирование
  того же сообщения, что и текст (`entities` или `caption_entities`; у опроса — пустой массив). Проекция (с 2026-10-16,
  вечер) — каждая entity в порядке Telegram **целиком**, со всеми полями, кроме объекта `user`, который заменяется
  на `user_id` (= `user.id`). Дробные числа в entity — отказ. Сервер сохраняет и публикует entity целиком, поэтому
  хеш обязан покрывать все поля (прежняя проекция из шести полей пропускала, например, `unix_time` у `date_time`).
  Иначе бот-посредник или тот, кто получил его токен, мог бы при том же тексте подменить
  адрес скрытой ссылки (`text_link`). Telegram нормализует entities при отправке (дробит пересечения, добавляет
  автоссылки), а копия сохраняет их байт в байт (проверено вживую 2026-10-16), поэтому клиент хеширует то, что увидит
  сервер: у копий сообщений владельца — entities как они пришли боту, у своих сообщений — из ответа Telegram (медиа
  с новой подписью клиент отправляет заново по `file_id`, а не `copyMessage`, чтобы получить итоговый вид).
  Вектор: `entities_sha256`.
- `files` = список `file_unique_id` в порядке альбома; для фото берётся последний (самый большой)
  элемент массива `photo`;
- `kind` совпадает с типом сообщения.

Несовпадение даёт `E_CONTENT_MISMATCH`. Так нельзя подменить содержимое, переотправив чужой конверт.

## Нагрузка и лимиты приёма
- Превышение лимита 30 конвертов в минуту на бота-отправителя: конверт молча отбрасывается (ответ занял бы отправку
  приёмного бота именно при флуде); клиент получает `NoReply` и повторяет позже.
- Элементы альбома приходят до конверта и лимит конвертов не проходят, поэтому у них свой: не больше 40 в минуту на
  бота-отправителя. Незавершённый альбом забывается через минуту; переполненный буфер вытесняет самые старые альбомы,
  а не отказывает новым (2026-10-19).
- Все обработчики сервера заняты: сразу `E_RATE` с `retry_after`, конверт не принят в работу, токен не тронут.
  Приём апдейтов сервер не останавливает никогда.
- Бесплатные операции: первые 3 в минуту у каждого бота-отправителя — всегда, остальные — в общем лимите сервера
  (600 в минуту на все приёмные боты вместе).

## Строгий JSON
Подпись считается по канонической форме, поэтому все реализации ОБЯЗАНЫ одинаково разбирать вход.
В протоколе разрешены только: объекты, массивы, строки, `true`/`false`/`null` и **целые** числа
в диапазоне ±(2^53−1). Отклоняются (`E_MALFORMED`): дубли ключей, дробные и экспоненциальные числа,
невалидный UTF-8, одиночные суррогаты в `\u`-escape, вложенность глубже 32. Python-клиент применяет те же правила
(`jcs.strict_loads`).

Публичные ключи Ed25519 (`auth.pk`, `id_pk`, `post_pk`) ДОЛЖНЫ быть в канонической кодировке и не малого порядка,
иначе `E_MALFORMED`. Для ключа малого порядка (например, нейтральной точки) «подпись» R = нейтральная точка, S = 0
верна для любого сообщения в некоторых реализациях (crypto/ed25519 в Go), а libsodium такие ключи отвергает: правило
выравнивает реализации. Проверка: точка декодируется, кодируется обратно теми же байтами и [8]P ≠ нейтральной точки.
На верхнем уровне конверта неизвестные поля запрещены (`E_MALFORMED`): расширения идут через `v`.

Прочие форматы (поле должно совпасть с шаблоном **целиком**; нарушение — `E_MALFORMED`, и проверяется оно **до**
подписи, то есть конверт с испорченным `op` отвергается как `E_MALFORMED`, даже если подпись неверна):
- base64url — без `=`, только каноническая форма (лишние младшие биты отклоняются); `resp_pk` — ровно 32 байта;
- `id` — ULID, 26 символов Crockford Base32 в верхнем регистре, первый символ `0`–`7`
  (`^[0-7][0-9A-HJKMNP-TV-Z]{25}$`, вектор `formats.id`);
- `kid` — `[A-Za-z0-9._-]{1,32}` (вектор `formats.kid`; kid «.» и «..» сервер не выдаёт);
- `op` — `^[a-z]+(\.[a-z]+)*$` (вектор `formats.op`).

Получатель отвергает вход длиннее предела **до** декодирования base64: тело `VEIL1 <…>` или `VEIL1R <…>` длиннее
base64url от (предел JSON + 1 байт кадра + 48 байт накладных расходов sealed box) — `E_DECRYPT`, как и шифртекст короче
49 или длиннее предела байт после декодирования. Для ответа предел JSON — 47 951 байт (вектор `limits.response_json_max`),
для текстового конверта — 3000, для конверта-документа — 65 536.

Порядок проверок на сервере (от него зависит, какой код увидит клиент): префикс → расшифровка →
формат → `v` → обязательные поля и типы → подпись → `ts` → `kid` → повтор `id` → токен (резерв за `id`) →
операция → лимит бесплатных операций или резерв токена → сбор контента (альбом — не дольше 3 с после прихода
конверта) → выполнение (внутри: устройство личности и привязка к боту — `E_DEVICE`, `E_BOT_NOT_BOUND`; контент; действие
и трата токена в одной транзакции).

Эталонная реализация клиента — `veil-client/veil/core/protocol/` (Python); она и сервер проекта проходят
`test-vectors/veil-v1.json`.

## Ответ из нескольких сообщений
Конверт ограничен одним сообщением, ответ — нет (лента, скрытое для ника). Ответ (JSON ≤ 47 951 байт: столько помещается
в 16 частей по 4000 символов base64url вместе с кадром и накладными расходами sealed box)
шифруется целиком, как обычно. Если `VEIL1R <base64url>` длиннее 4096 символов, base64url режется на куски
по 4000 символов и отправляется сообщениями `VEIL1R <i>/<n> <кусок>` (1 ≤ i ≤ n ≤ 16), все — ответом на конверт.
`i` и `n` записаны десятичными числами без ведущих нулей и знака (`01/02` — не часть ответа). Ответ, которому
понадобилось бы больше 16 частей, отправитель не формирует: вместо него сервер отвечает подписанной ошибкой
`E_RESPONSE_TOO_LARGE` (09).
Клиент собирает части в любом порядке, склеивает куски и расшифровывает как одиночный ответ.
Одиночный ответ отличается от части тем, что в base64url нет символа `/`. Вектор: `response_parts`.

Правила сборки у клиента:
- Ответ и части принимаются на любой отправленный конверт операции (первый и повторы, 09): части от разных копий
  ответа собираются вместе, ответ сервера на повтор совпадает байт в байт.
- Части группируются по `n`; кусок хранится под парой (`n`, `i`). Повтор той же пары заменяет прежний кусок
  (побеждает последний). Ответ собирается, когда в группе `n` есть все `i` от 1 до `n`; посторонняя часть с другим `n`
  настоящую группу не портит. Всего хранится не больше 136 кусков (сумма `n` при `n` от 1 до 16).
- Текст, не совпадающий с шаблоном части (`01/02`, `17/17`, `0/2`), разбирается как одиночный ответ и отсекается тем же
  правилом, что и любой чужой ответ.
- Одно правило ошибок для одиночного и собранного ответа: не расшифровалось или подпись не сошлась (`E_NOT_ENVELOPE`,
  `E_DECRYPT`, `E_SIG`, `E_MALFORMED` до проверки подписи) — неподписанное, клиент игнорирует его и ждёт настоящий
  ответ. Ответ с верной подписью сервера, но испорченного состава (`E_MALFORMED`, `E_VERSION` после подписи) —
  подписанное: операция завершается этой ошибкой.

## Защита от петель bot-to-bot
- Приёмный бот отвечает **только** на сообщения `VEIL1 ...` и только один раз (`VEIL1R`).
- Если ответить по протоколу нельзя (сообщение `VEIL1 …` не расшифровалось, неподдерживаемая `v` — то есть
  `resp_pk` неизвестен), сервер шлёт **незашифрованную подсказку** `VEIL1E <код>` не чаще 1 раза
  в 10 минут на бота, затем молчит. Подсказка не подписана: клиент использует её только как намёк
  (например, обновить `keys.json`), а не как ответ. Клиент принимает подсказку, только если `<код>` совпадает с
  `^E_[A-Z_]{1,32}$`, иначе игнорирует её. Сообщения без префикса `VEIL1 ` от ботов — это контент
  к будущему конверту (в том числе текст поста), на них сервер не отвечает никогда (уточнено 2026-10-15).
- Ошибки после разбора `id` и `resp_pk` (`E_SIG`, `E_CLOCK`, `E_MALFORMED` в теле) возвращаются обычным
  зашифрованным подписанным `VEIL1R`.
- Человеку, написавшему приёмному боту напрямую, — короткая подсказка не чаще раза в 10 минут.
- Ответы сервера никогда не являются конвертами, и клиент на `VEIL1R`/`VEIL1E` не отвечает.
  Сервер тоже игнорирует входящие `VEIL1R`/`VEIL1E`.
- Повтор конверта с тем же `id` в течение 24 ч получает тот же сохранённый ответ (без повторного выполнения).
- Лимит: 30 конвертов в минуту на бота — сверх него конверт молча отбрасывается (см. «Нагрузка и лимиты приёма»), бан
  бота на 1 час при превышении в 3 раза.
