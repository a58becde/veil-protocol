# 05. Операции: посты, ответы, правки, лента

## Сводка операций
| `op` | auth.mode | Токен | Назначение |
|---|---|---|---|
| `post.create` | `identity` или `ephemeral` | да | опубликовать пост или ответ |
| `post.edit` | `post_secret` | да | исправить пост целиком или дописать UPD |
| `post.delete` | `post_secret` | да | удалить пост |
| `post.check` | `ephemeral` | нет | заранее посчитать, поместится ли пост |
| `device.set` | `identity` (новый ключ устройства) | да | зарегистрировать личность и устройство, отозвать прежнее, привязать бот |
| `device.get` | `identity` | нет | что сервер знает о личности этого устройства |
| `enc.set` | `identity` | нет (1 раз в час) | сменить ключ шифрования |
| `nick.set` | `identity` | да | задать, сменить или убрать ник |
| `nick.lookup` | `identity` или `ephemeral` | нет | найти и проверить ключи по `ник·метка` (для «лично для») |
| `hidden.file` | `ephemeral` | нет | получить файл-контейнер «лично для» |
| `feed.get` | `ephemeral` | нет | получить публичную ленту постов |
| `keys.get` | `ephemeral` | нет | получить `keys.json` |
| `ping` | `ephemeral` | нет | проверка связи и версии |

`identity` везде означает: конверт подписан ключом устройства (`auth.pk = dev_pk`, 02). Сервер находит личность
по `dev_pk`; неизвестное или отозванное устройство — `E_DEVICE`, личность привязана к другому боту —
`E_BOT_NOT_BOUND`.

**Однократность (2026-10-16).** Повтор конверта с тем же `id` (после таймаута, перезапуска сервера) не выполняет
действие второй раз: `post.create` находится по `op_id` поста, `post.edit` и `post.delete` — по `op_id` задания
очереди, операции личности идемпотентны по содержимому. Токен тратится в одной транзакции с действием (03). Повтор
обязан быть тем же действием над тем же постом и подписан ключом этого поста — иначе `E_REPLAY` или `E_NOT_OWNER`.

**Журнал клиента.** `post_secret`, `id` конверта, токен, тело и контент клиент записывает **до** первой отправки
конверта. Если итога нет (`E_PENDING` после всех повторов, нет ответа, перезапуск бота), клиент позже повторяет этот
же конверт и получает итог; право править и удалять пост не теряется. Повтор обязан нести тот же `id`, токен, `resp_pk`,
тело и контент. Сохранённый ответ зашифрован на `resp_pk` первого конверта, поэтому повтору нужен его секрет. Эталонный
клиент не хранит ни его, ни одноразовый ключ подписи анонимного конверта, а выводит оба из `post_secret` (HKDF-SHA256,
info `"veil/v1/journal/resp"` и `"veil/v1/journal/auth"`); клиент, который хранит их, держит их наравне с `post_secret`. Сервер помнит ответы
24 часа, поэтому журнал старше суток удаляется. Токен такого конверта клиент считает потраченным: он закреплён за
`id`. Черновик с нажатым «Отправить» хранится, пока конверт не записан в журнал: перезапуск во время случайной
задержки не теряет пост.

## Ключ поста
Для каждого поста клиент создаёт `post_secret` (32 случайных байта) и выводит из него
`post_sk` (Ed25519, HKDF-SHA256, info `"veil/v1/post"`). В `post.create` передаётся `post_pk`.
Сервер хранит `post_pk` у поста. Правка и удаление подписываются `post_sk` (`auth.mode = "post_secret"`,
`auth.pk = post_pk`).

Итог: управлять постом может только тот, у кого есть `post_secret`. Сервер не знает и не хранит,
какой бот или человек его создал. `post_secret` хранится в кошельке клиента и входит в экспорт.

## post.create
```json
"body": {
  "post_pk": "<b64url>",
  "reply_to": 13,
  "hidden": null,
  "options": {"link_preview": false}
}
```
- Ник: при `auth.mode = identity` сервер берёт текущий ник и метку личности устройства `auth.pk`. Если ника нет,
  пост выходит без подписи. Эталонный клиент в этом случае шлёт пост анонимно (`ephemeral`): связывать с личностью
  пост без видимого ника незачем.
- `reply_to`: номер поста, на который отвечаем. Сервер ставит нативный reply (`reply_parameters`,
  `allow_sending_without_reply = true`), добавляет в шапку `>>> №13` (ссылка на пост) и обновляет
  строку ответов у поста №13 (см. 06).
- Ответ: `{"n": 246, "url": "https://t.me/<group>/<message_id>"}`.
- Поля `body`: `post_pk` обязательно; `reply_to`, `hidden`, `options` — по желанию; другие поля — `E_MALFORMED`.
  `post_pk` уникален среди всех постов, в том числе удалённых и неудавшихся: «лично для» привязано к нему (07). Уже
  занятый — `E_MALFORMED` до публикации, номер не тратится.
  `options` сейчас содержит только `link_preview` (по умолчанию `false`).

### Поддерживаемый контент
| kind | Как публикуется | Шапка |
|---|---|---|
| `text` | `sendMessage` (текст + entities) | в тексте |
| `photo`, `video`, `animation`, `document`, `audio`, `voice` | `copyMessage` с новой подписью | в подписи (лимит 1024) |
| `album` | `sendMediaGroup` по `file_id` приёмного бота, подпись у первого элемента (`copyMessages` не умеет менять подпись) | в подписи первого |
| `video_note`, `sticker` | сначала сообщение-шапка, затем медиа ответом на неё | отдельным сообщением |
| `poll` | сначала шапка, затем `copyMessage` опроса | отдельным сообщением |

Альбом: 2–10 элементов; фото и видео можно смешивать, документы и аудио — только с элементами своего вида
(ограничение `sendMediaGroup`), иначе `E_UNSUPPORTED`.

**Кто публикует.** Пост публикует тот приёмный бот, который принял контент: `file_id` есть только у него,
а скопировать сообщение из чужой личной переписки другой бот не может (решено 2026-10-15). Поэтому
приёмные боты одновременно являются публикующими, пул ботов — это пул «inbox + publisher». Правка
и удаление идут через бота, опубликовавшего пост. Правка `media` возможна только через того же
приёмного бота (иначе `E_UNSUPPORTED`); текстовые правки и удаление — через любого.

**Спойлер и подпись над медиа.** Медиа публикуется по `file_id` из проверенного снимка, а не копией сообщения.
Поэтому `has_media_spoiler` и `show_caption_above_media` исходного сообщения сервер переносит сам (`has_spoiler`,
`show_caption_above_media` в `send*` и в элементах альбома; Bot API принимает их для фото, видео и анимации).

**Ответ сервера приходит после публикации.** Если Telegram не принял пост, клиент получает `E_TELEGRAM`
(токен не потрачен), номер `№N` остаётся пропущенным. Повтор конверта с тем же `id` не создаёт второй пост.
Если запрос публикации ушёл в Telegram, но ответа нет (обрыв связи, таймаут, 5xx), сервер не повторяет его сам —
повтор дал бы дубль — и отвечает `E_UNCONFIRMED`: пост мог выйти, автор проверяет группу (2026-10-19). Токен не
тратится, у сервера пост помечен неудавшимся.

Квиз-опросы в v1 не поддерживаются (`E_UNSUPPORTED`): `copyMessage` квиза требует, чтобы бот знал
правильный ответ. Проверить отдельно.

Премиум-эмодзи (`custom_emoji`) сервер передаёт как есть. Без юзернейма с Fragment Telegram покажет
их обычными эмодзи. Это допустимо (решение от 2026-10-14).

## post.edit
```json
"body": {"n": 246, "mode": "replace" | "append" | "media"}
```
- `replace`: приложенный контент полностью заменяет текст или подпись. Клиент показывает это как «Исправить».
- `append`: приложенный текст дописывается секцией `UPD: …` (префикс из локали сервера). Клиент
  показывает это как «UPD».
- `media`: приложенное медиа заменяет медиа поста (`editMessageMedia`), подпись сохраняется.
- Лимит: **не более 5 правок в течение 24 часов с момента публикации**. Позже: `E_EDIT_WINDOW`,
  сверх лимита: `E_EDIT_LIMIT`.
- Контент правки: для `replace` и `append` — одно текстовое сообщение; для `media` — одно медиа вида
  photo, video, animation, document, audio (пост тоже должен быть одиночным медиа этих видов).
  У кружков, стикеров и опросов текста нет: `replace`/`append` дают `E_UNSUPPORTED`.
- Ответ: `{"n": 246, "edits_left": 3}`. Ответ на `post.delete`: `{"n": 246, "deleted": true}`, а если часть
  сообщений осталась в группе — ещё `"left": 1` (см. ниже).
- Если результат не помещается в лимит Telegram, правка отклоняется **до** обращения к Telegram
  с `E_TOO_LONG` и полем `overflow` (на сколько символов превышен лимит). См. 06.
- Пока предыдущая правка или удаление поста ждёт в очереди, следующее действие с ним получает `E_PENDING` и
  повторяется клиентом тем же конвертом: иначе правка строилась бы от старого содержимого и затёрла бы UPD.
  Запись правки и закрытие задания — одна транзакция: после перезапуска правка не применится и не посчитается дважды.

## post.delete
```json
"body": {"n": 246}
```
Удаляются только сообщения этого поста (шапка и медиа). Ответы остаются; их `>>> №246` ведёт
на удалённое сообщение. В ленте пост помечается `deleted`, текст на сервере стирается сразу.

Сервер удаляет сообщения по одному (`deleteMessage`), а не `deleteMessages`: тот молча пропускает сообщения, которые
удалить нельзя, — Bot API разрешает удаление только моложе 48 часов. «Сообщение не найдено» считается удалённым
(повтор задания после временной ошибки). Сообщение, которое удалить нельзя, заменяется заглушкой — у правки своих
сообщений срока нет:
- текст — правкой в `№246 — пост удалён автором` (локаль `render.deleted`), кнопки снимаются;
- фото, видео, анимация, документ, аудио — `editMessageMedia` на картинку-заглушку с той же подписью, а если
  Telegram не принимает фото (альбом документов или аудио) — на файл-заглушку;
- голосовое, кружок, стикер, опрос заменить нельзя: они остаются, подпись голосового правится в заглушку.

Сколько сообщений осталось, сервер возвращает в `left`; клиент сообщает владельцу, что удалить их может админ
группы. Посты сами по себе не удаляются никогда.

## device.set — регистрация личности и устройства (2026-10-16)
Конверт подписан **новым** ключом устройства (`auth.pk = dev_pk`) — это доказывает владение им.
```json
"body": {"id_pk": "<b64url>", "seq": 1792000000, "dev_sig": "<b64url>",
         "enc_pk": "<b64url>", "enc_exp": 1793209600, "enc_sig": "<b64url>"}
```
Сервер проверяет `dev_sig` (корнем `id_pk`) и `enc_sig` (ключом `dev_pk`) по формулам 02, `seq` не дальше суток
в будущее, `enc_exp` в будущем и не дальше 31 дня. Затем:
- личности нет — создаёт её (метку считает сам, 02), привязывает к боту-отправителю;
- `seq` больше текущего — заменяет устройство и ключ шифрования, перепривязывает к боту-отправителю, сбрасывает
  срок смены ника (новое устройство — это восстановление: владелец может сразу вернуть ник после вора);
- тот же сертификат (`seq` и `dev_pk` совпадают) — успех без изменений, но только с того же бота
  (`E_BOT_NOT_BOUND` иначе: сертификат лежит в файлах бота, повтор с чужого бота — попытка увести личность);
- `seq` меньше, или равен при другом `dev_pk` — `E_STALE`;
- `dev_pk` уже принадлежит другой личности — `E_MALFORMED`.

Ответ: `{"tag": "7f3a9c", "nick": "Вася" | null}`.

## device.get
`"body": null`. Ответ: `{"id_pk", "tag", "nick", "seq", "enc_pk", "enc_exp"}` личности этого устройства.
`E_DEVICE`, если устройство неизвестно или отозвано (`seq` у личности уже другой), `E_BOT_NOT_BOUND` — личность
привязана к другому боту. Клиент вызывает её при запуске: так он узнаёт, что его отозвали или что база сервера
откатилась (тогда повторяет `device.set` своим сертификатом).

## enc.set
```json
"body": {"enc_pk": "<b64url>", "enc_exp": 1793814400, "enc_sig": "<b64url>"}
```
Новый ключ шифрования, подписанный ключом устройства (02). `enc_exp` должен быть больше текущего (`E_STALE`),
в будущем и не дальше 31 дня. Не чаще 1 раза в час на личность (`E_RATE`). Ответ: `{"enc_exp": 1793814400}`.

## nick.set
```json
"body": {"nick": "Вася"}
```
`null` убирает ник. Нормализация и ограничения: 02. Не чаще 1 раза в 24 ч (`E_NICK_COOLDOWN` с `retry_after`);
повтор того же ника сменой не считается. Пара ник·метка уникальна с точностью до похожих букв (`E_NICK_TAKEN`, 02).
Ответ: `{"nick": "Вася", "tag": "7f3a9c"}` (ник после нормализации).

## nick.lookup
```json
"body": {"nick": "Петя", "tag": "k2m9xq"}
```
Ответ: `{"matches": [{"id_pk", "nick", "dev_pk", "seq", "dev_sig", "enc_pk", "enc_exp", "enc_sig"}, ...]}`
(обычно одна запись; до 5). Только личности с действующим ключом шифрования. Нет — `E_NOT_FOUND`. Клиент проверяет
каждую запись (02, «Проверка получателя») и отбрасывает не прошедшие проверку.
Смена ника не меняет уже опубликованные посты (`nick_at_post` фиксируется при публикации).

## feed.get: публичная лента
```json
"body": {"since": 240, "limit": 200}
```
Оба поля необязательны (`since` = 0, `limit` = 100, максимум 200). Ответ одинаковый для всех клиентов:
```json
{"posts": [ ...записи... ], "next": 251}
```
Запись (пустые поля **не передаются**, чтобы страница была меньше):
```json
{"n":246,"url":"...","kind":"text","nick":"Вася","tag":"7f3a9c","reply_to":245,
 "excerpt":"первые 120 символов без форматирования","edited":true,
 "hidden_for":"<b64url enc_pk получателя>","hidden_blob":"<b64url>","post_pk":"<b64url>",
 "hidden_file":true,"bot":1234567890}
```
У удалённого поста только `n`, `kind`, `url`, `"deleted": true`. `hidden_*` и `post_pk` есть только у скрытого «для ника»
(получатель сверяет `post_pk` с тем, что внутри расшифрованного, 07); `hidden_file` и `bot` — у «лично для» с файлами:
`bot` — ID приёмного бота, который держит контейнер (просить `hidden.file` нужно у него).
Размер страницы:
- записи страницы вместе (в канонической форме JCS) — не больше **12 000 байт** (ответ приходит в несколько
  сообщений, 04);
- первая запись входит всегда, даже если она одна больше 12 000 байт: тогда страница состоит из неё одной;
- запись, которая сама по себе не поместилась бы в ответ (04), отдаётся **без** `hidden_for`, `hidden_blob`,
  `post_pk`, `hidden_file`, `bot` — как обычный пост. Лента не останавливается ни для кого;
- если в странице есть записи, `next` больше `since`.

`next` — с какого `since` продолжать; `null` — лента прочитана до конца.

Клиент хранит номера своих постов и находит ответы на них локально. Так сервер не узнаёт,
чьи это посты (вариант Б анонимности). Лимит: 6 запросов ленты в минуту на бота (`E_RATE`, `retry_after`):
хватает прочитать несколько страниц подряд, а опрос раз в 30–60 секунд остаётся нормой.

## post.check — проверка до отправки (2026-10-16)
Бесплатная операция (`ephemeral`, без токена): клиент вызывает её при показе черновика, чтобы не предлагать
«Отправить» для того, что не пройдёт. Тело — форма будущего поста без самого контента:
```json
"body": {"kind": "text", "body_units": 4061, "nick": "Имя·nky1p0", "reply_to": 5,
         "hidden": {"mode": "all" | "to", "media": true, "file": true, "to_label": "Петя·k2m9xq"}}
```
`body_units` — длина видимого текста в UTF-16 после скрытия. Ответ: `{"overflow": 27, "limit": 4080}`
(`overflow` 0 — помещается) или `E_UNSUPPORTED`, если такой вид контента так не скрыть. Сервер считает
тем же рендером и той же таблицей скрытия (07), что и при публикации, с номером «последний + 1».
При публикации длина проверяется ещё раз — с точным номером, внутри транзакции (отказ номер не тратит).

## hidden.file — файл «лично для» (2026-10-16)
Бесплатная операция: `"body": {"n": 52}`. Сервер отправляет зашифрованный файл-контейнер поста документом
в тот же чат ответом на конверт, затем обычный ответ `{"n": 52, "sent": true}`. Отдаётся любому: без ключа
из `hidden_blob` (запечатан на получателя) контейнер не прочитать; лимит 10 в минуту на бота и 60 в минуту
на весь сервер (крупные файлы занимают отправку приёмного бота).
Держит файл бот, который его принял: запрашивать нужно у того же приёмного бота (поле `bot` записи ленты; иначе
`E_UNSUPPORTED`).

## Случайная задержка
Опция клиента: перед отправкой конверта выждать случайное время из заданного диапазона.
Сервер в этом не участвует.

- `op: "post.react"`: реакция от имени серверного бота.
